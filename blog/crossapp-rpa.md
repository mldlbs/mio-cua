# 跨应用 RPA：AI 怎么自己读文件 → 求和 → 保存

> Draft for 掘金/思否. Repo: https://github.com/mldlbs/mio-cua

---

传统 RPA 让你拖节点、配流程：一个"读文件"节点、一个"启动计算器"节点、一个"点按钮"节点……每一步都写死，界面一改就崩。

mio-cua 的跨应用场景是另一回事。一条自然语言指令，AI 自己看完做完：

```
目标：读取桌面 smoke_numbers.txt（每行一个整数，共三个：12、34、56），
用计算器求出它们的和（102），把结果保存到新文件 smoke_sum_result.txt。
```

它真的做到了：**读文件 → 计算器求和 → 保存结果**，三个应用、21 步、全绿。

---

## 这条指令到底难在哪

三个子任务都不难，难的是**衔接**：

| 步骤 | 难点 |
|---|---|
| 读文件 | 用记事本打开文件后，OCR 读到的是"12/34/56"的**像素**，agent 要从场景里把它们认成数字 |
| 求和 | 计算器每个按键都要确认显示区更新；按 `+` 时显示区**不该变**，否则 agent 会以为点空了而重复按键 |
| 保存 | 新建记事本 → 输入 102 → Ctrl+S → 在"文件名:"字段改名 → 回车确认——任何一个环节漏了，文件就存不下来 |

## 让这条路走得通的关键设计

### 1. 键盘输入优先于点按钮

计算器场景里，指令明确要求用 `key(keys="1")` 逐键输入，而不是点击屏幕上的数字按钮。

这不是偷懒，是工程判断：**键盘是确定性输入，像素点击是概率性输入。** 一个 key 事件要么发出去要么报错，而"点到数字 5 的坐标"可能因为布局偏移点到 4。

中间还踩过一个坑：`+` 号当分隔符被 split 失败，导致 `key(keys="+")` 发不出去。修完之后按键链路才算完整。

### 2. 显示区验证（Scene Diff）

计算器的显示区会被识别成一个 `display` 节点。点数字键之后，系统通过 **Scene Diff** 检查显示值变化：`0` → `7`，确认这次点击真的生效了。

更细的规则：按**操作符**（× ÷ + −）时显示区本来就不该变——它只是记下待执行的操作。如果 agent 不知道这条，它会把"显示没变"误判为"按键没点到"而重复按 `+`。所以感知层对操作符标注 `expected: display unchanged`，明确告诉模型"这是正常的"。

### 3. 一动作一感知（One action, one perception）

最关键的一条循环规则：**每做一个动作，重新看一次屏幕，再决定下一步。**

听起来浪费，但配合内容签名缓存，没变的窗口会直接复用上次的 OCR 结果；一旦计算器显示从 `0` 变成 `7`，签名变了，缓存立刻失效。这样做的收益是消灭了一整类经典故障——"基于过期场景规划五个动作，然后点到一个早已挪走的位置"。

### 4. 保存对话框是重灾区，专门做了守卫

保存那一步，Win11 的新式对话框几乎不给 UIA 控件——"文件名(N):"标签只有 OCR 文本，输入框也不在 UIA 树里。感知层靠两个启发式补救：

- **字段标签推断**：`文件名(N):` 这种"短文本+冒号"的节点，其右侧同行文本节点被判为可输入的编辑框（`labelFor` 关系定位）。
- **按钮词表**：`保存(S)` / `取消` / `OK` 这些只有 OCR 文本的按钮，命中词表后变成可点击候选。

loop 层还有硬守卫：如果 agent 输入了文件名却**没按回车**，`success` 会被拦截，提示必须先 `key(keys="enter")` 确认——因为没确认的编辑根本不会生效，直接报成功就是假成功。

## 对"新一代 RPA"的启示

传统 RPA 自动化的是**你写的流程**：界面一改，流程崩。mio-cua 自动化的是**你描述的意图**：它每步重新看屏幕、重新决策，界面怎么变它跟得上。

财务月结、政务办事、数据录入……任何"人对着屏幕重复操作"的活，都是这个思路的目标场景。
